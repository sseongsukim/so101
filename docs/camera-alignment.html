SO-101 카메라 정합

실제 카메라 2대를 Isaac Lab의 SO-101 stack cube 씬과 맞추는 작업. 원격에서 할 수 있는 것은 전부 끝났고, 이 문서의 후반부가 현장에서 실행할 순서입니다.

브랜치 dsafjk0024 최신 커밋 2ad2017 원격 #1–#7, #9–#11 완료 현장 #12–#16 대기

정합을 어떤 방식으로 하는가

실물이 기준이고 sim이 따라갑니다. 다만 Isaac이 표현하지 못하는 것이 있어서, 두 쪽은 가상 정규화 카메라라는 중간 지점에서 만납니다.

IsaacLab의 Camera는 이상적인 핀홀만 렌더합니다. 소스에서 확인한 제약:

  • camera.py:575-605 — f_y = f_x, c_x = W/2, c_y = H/2 하드코딩
  • sensors.py:108-111 — aperture offset 무시 (NVIDIA 티켓 OM-42611)
  • utils/sensors.py:57-58 — from_intrinsic_matrix가 cx/cy를 0으로 버리고 fx/fy를 평균냄

그래서 렌더러를 구부리는 대신, 실물 프레임을 Isaac이 정확히 재현할 수 있는 형태로 옮깁니다. 왜곡 제거와 중심 정렬이 같은 remap 한 번에 처리됩니다. 

K_virtual = [[f, 0, 320], [0, f, 240], [0, 0, 1]],  dist = 0,  alpha = 0

실물 initUndistortRectifyMap + remap   (캡처 모듈 내부에서 항상 적용)
sim  focal_length = f × 20.955 / 640    (wrist/front 각각 다른 f)
좌표 convention "opengl" → "ros"        (OpenCV 출력을 변환 없이 대입)

Isaac Sim 5.1에는 전체 OpenCV 왜곡 모델(opencvPinhole)이 있지만 IsaacLab이 쓰지 않습니다. rectify 후 hFOV 손실이 10%를 넘으면 그 경로를 검토합니다 — 이슈 #16의 분기 1.

작업 중 잡아낸 실제 오류

모두 그대로 뒀다면 현장에서 원인 불명으로 나타났을 것들입니다.

  1. 노출 잠금이 드라이버 기본값을 고정하고 있었음

    AE가 동작 중일 때 exposure_time_absolute는 inactive 플래그 상태라, 읽으면 측광값이 아니라 드라이버 기본값이 돌아옵니다. 그 값을 고정하니 wrist가 순백으로 날아갔고, 그 상태로는 보드 검출이 전부 실패합니다. 목표 밝기로 직접 이분 탐색하도록 바꿨고, 배경의 밝은 창에 끌려가지 않게 중앙 영역으로 측광합니다. 결과: wrist 포화 0.00%, front 중앙 포화 9.16% → 3.84%.

  2. 제가 넣은 CAP_PROP_BUFFERSIZE=1이 프레임레이트를 깎고 있었음

    프레임 신선도를 위해 넣었는데 wrist가 30.1 → 21.2 fps로 떨어졌습니다 (드라이버 자체는 30.15 유지). 설정을 빼고, 신선도가 필요한 곳에서만 read_fresh()로 큐를 비웁니다.

  3. 검증이 다른 저장소의 코드를 돌고 있었음

    so101 패키지가 옆 체크아웃 research/so101에서 editable로 설치돼 있어, 초기 프레임 감사가 제 리팩터를 전혀 거치지 않은 구버전을 실행했습니다. 경로 우선순위를 바로잡고 재실행하니 숫자가 6자리까지 동일했고, 그제서야 ROS 변환 검증이 근거를 갖게 됐습니다.

  4. T_env_base가 항등이 아님 — 잠재된 90° 오차

    assets/so101.py:55의 rot=euler_angles_to_quat([0,0,90]) 때문에 로봇 베이스가 env 프레임 대비 Z축 90° 회전해 있습니다. prim이 (0,0,0)에 있어 "base == env origin"이 안전해 보이는 함정입니다. 별도 URDF FK를 썼다면 모든 카메라 pose에 90° yaw 오차가 조용히 들어갔을 것이고, Isaac FK를 쓰기로 한 결정이 이를 피해갑니다.

  5. Isaac 렌더 경로의 세 가지 함정

    ① Omniverse가 텍스처를 비동기로 스트리밍해서, 머티리얼 생성 직후 한 프레임만 렌더하면 회색 폴백이 나옵니다. ② CuboidCfg가 만드는 지오메트리에는 UV 좌표가 없어 OmniPBR이 텍스처를 입힐 곳이 없습니다. ③ getChessboardCorners의 보드 프레임은 +y가 아래라서 +z가 읽는 면의 반대쪽을 향합니다. +z를 위로 눕히면 거울상이 되고, 거울상 ArUco는 아예 디코딩되지 않습니다 — 보드는 완벽하게 렌더되는데 코너가 0개 나옵니다.

  6. 포즈 생성기의 두 가지 잘못된 제약

    테이블 간섭 검사에 base 링크를 포함해서 자세와 무관하게 전부 탈락했고, 보드 전체 가시를 요구해서 손목캠 후보가 0개였습니다. ChArUco는 부분 검출이 가능한 것이 장점입니다. 고친 뒤: wrist 24포즈(최소 회전차 18.6°), front 24포즈(76.3°).

태그를 어떻게 고르는가

AprilTag로 바꿀지 판단하려면 숫자 하나만 보면 됩니다 — 태그 한 칸이 카메라에서 몇 픽셀을 차지하는가. 아래는 설명용 그림이 아니라, 실제로 태그를 렌더하고 실제 검출기를 돌려 나온 결과입니다.

1. 태그는 어디에 붙고, 무엇을 알려주나

카메라가 태그를 보면 solvePnP가 태그가 카메라 기준 어디에 어떤 자세로 있는지를 돌려줍니다. 그 관계를 여러 로봇 자세에서 모으면 카메라가 어디에 달렸는지 풀 수 있습니다. 두 카메라는 붙는 위치가 정반대입니다.

2. 셀이 무엇이고, 왜 개수가 중요한가

태그는 흑백 정사각형(셀)의 격자입니다. 가운데가 데이터 비트이고, 그 바깥을 검은 테두리 1셀이 둘러쌉니다. 검출기는 테두리로 사각형을 먼저 찾고, 안쪽 비트를 한 칸씩 읽어 ID를 해독합니다. 한 칸이 최소 몇 픽셀은 되어야 읽힙니다.

두 그림은 같은 크기로 인쇄한 태그입니다. AprilTag 36h11은 같은 종이를 8×8로 쪼개니 한 칸이 더 작습니다 — 그래서 더 가까이 가거나 더 크게 인쇄해야 합니다. 빨간 선 바깥의 테두리도 셀에 포함된다는 점이 자주 간과됩니다.

3. 멀어지면 실제로 이렇게 보입니다

태그를 각 픽셀 크기로 실제 축소한 뒤 그대로 확대한 것입니다 — 보간 없이, 검출기가 보는 그대로. 막대는 ID 20종 × 서브픽셀 오프셋 3종 = 60회 시행의 검출 성공률입니다.

결론 — 그리퍼에 태그를 붙입니다 (테이프로 충분)

  • front 카메라는 그리퍼에 테이프로 붙인 태그를 직접 봅니다 (eye-to-hand). 두 카메라가 각자 독립적으로 풀리고, front가 wrist의 캘리브레이션 결과에 기대는 일이 없습니다
  • 한때 "그리퍼에 아무것도 안 붙인다"는 이유로 테이블 보드를 두 카메라의 공유 기준으로 쓰는 경로(아래 §5)를 대신 채택했었습니다. 하지만 붙이는 게 테이프 한 조각이면 그 제약을 지킬 이유가 없고, 공유 경로는 오차가 wrist 결과 위에 쌓이는 대가가 있습니다(§5) — 그래서 되돌렸습니다
  • 이 페이지 위쪽 픽셀 예산(30 mm 태그, DICT_4X4_50)은 정확히 이 용도로 계산된 것입니다. 그리퍼 태그는 이제 기본으로 인쇄됩니다
  • 테이블 보드는 여전히 필요합니다 — 양쪽 카메라의 intrinsic과 wrist의 hand-eye(테이블에 고정, eye-in-hand)에 씁니다. 이 용도엔 "0.73 m 밖에서 front가 읽어야 한다"는 제약이 없으므로, 보드 크기는 순수하게 intrinsic 정확도만 보고 정하면 됩니다

5. 대안 — 공유 보드 경로 (그리퍼에 정말 못 붙일 때)

손목캠이 먼저 테이블 보드의 위치를 재고, front가 같은 보드를 보고 자기 위치를 푸는 방식입니다. 그리퍼에 아무것도 안 붙여도 되지만, 오차가 wrist 결과 위에 쌓입니다 — 직접 eye-to-hand는 한 번에 풀리는데 이 경로는 wrist hand-eye 오차 + PnP 2회가 더해집니다. 합성 데이터로 실측한 전파량:

보드 pose에 2 mm / 0.3° 오차 → front 카메라는 평균 5.8 mm, 최악 14.1 mm 어긋남

scripts/calibrate_handeye.py --camera front --solve --via-board로 남아있습니다. 쓰게 된다면 wrist를 먼저, 잘 해야 합니다 — 솔버 간 편차가 크면 그 오차가 front에 그대로, 오히려 증폭돼 전달됩니다.

모든 현장 작업의 블로커입니다. 이것부터 끝나야 나머지가 시작됩니다.

python scripts/make_calibration_targets.py

# → calibration/targets/gripper_aruco.pdf  (A4 세로, 30 mm 태그 3장, 기본 포함)
# → calibration/board.yaml                 (검출기가 읽는 규격 — 인쇄물과 자동 일치)
배율 100%로 인쇄. 프린터 대화상자의 "페이지에 맞춤" / "scale to fit"을 반드시 끄세요. 켜면 치수가 틀어지고 이후 모든 숫자가 조용히 틀립니다. 무광 용지만 — 광택지는 조명 반사로 검출이 실패합니다.

확인할 것

  • 각 페이지 하단 100 mm 기준자를 자로 측정. 정확히 100 mm가 아니면 재인쇄하거나, 실측 사각 크기를 이후 명령에 --square-mm으로 전달
  • 테이블 보드는 평판에 기포 없이 부착 — 휘면 평면 가정이 깨집니다. wrist intrinsic·hand-eye에 씁니다
  • 그리퍼 태그 3장을 서로 다른 각도로 작은 큐브/브래킷에 붙이고, 그 브래킷을 그리퍼에 테이프로 고정. 영구 마운트일 필요는 없고, 촬영 중 움직이지만 않으면 됩니다. 단일 평면 태그는 정면에서 회전 추정이 튀고, 그 오차가 hand-eye 해에 그대로 들어가서 3장을 씁니다
  • 보드 마커 ID 0–19, 그리퍼 태그 ID 20–22로 겹치지 않으니 둘이 같이 보여도 무방

intrinsic 촬영 #13

python scripts/calibrate_intrinsics.py --camera front
python scripts/calibrate_intrinsics.py --camera wrist

# 인쇄 사각이 32 mm가 아니었다면
python scripts/calibrate_intrinsics.py --camera front --square-mm 31.7

# 이미 찍은 사진으로 다시 풀기만
python scripts/calibrate_intrinsics.py --camera front --solve-only

Enter로 촬영, q로 종료, d로 직전 장 삭제. 매 장마다 어느 영역이 아직 비었는지와 기울인 장수를 알려줍니다.

접선 왜곡(p1/p2) 추정은 기본으로 꺼둡니다(CALIB_ZERO_TANGENT_DIST). 적은 장수로 같이 추정하면 principal point와 얽혀 서로를 오염시키는데, 웹캠급 렌즈는 접선 왜곡 자체가 원래 작아서 꺼도 손해가 없습니다 — 40장 기준 최악의 cx 오차가 약 5 px에서 약 3 px로 줄었습니다(fx 정확도·RMS는 그대로).

촬영 프로토콜

  • 640×480에서 직접 촬영 (스크립트가 강제). 720p로 찍고 K를 스케일하면 안 됩니다 — USB 카메라는 해상도 모드마다 센서 크롭·비닝이 달라 실효 FOV가 바뀝니다
  • 약 40장, 보드가 각 사분면과 중앙을 덮도록. A4 보드는 작아서 principal point(cx/cy)가 잘 안 잡힙니다 — 60회 독립 시행 측정: 28장 58%, 32장 68%, 36장 77%, 40장 82%, 48장 78%(더 안 늘어남, 이 보드의 한계). 40장이 목표치입니다
  • 광축 대비 ±30~45° 기울임 5장 이상. 정면만 찍으면 초점거리와 거리가 얽혀 fx가 불안정해집니다
  • 화면의 1/3~2/3을 채우는 여러 거리에서

합격 기준 — 셋 다 통과해야 yaml이 써집니다

  • OpenCV RMS 재투영 < 0.3 px
  • 프레임 전 영역 커버
  • 25° 이상 기울인 장 5장 이상

불합격이면 *.rejected.yaml로 떨어지고 정식 파일은 건드리지 않습니다.

RMS < 0.3 px 게이트를 통과해도 cx/cy가 틀릴 수 있습니다. fx·왜곡·principal point는 서로 상쇄하며 재투영 오차를 낮출 수 있어서(고전적인 캘리브레이션 퇴화), 합성 데이터로는 RMS 게이트를 통과한 세션의 약 1/3이 cx를 2 px 넘게 놓쳤습니다(상관계수 0.08 — 거의 무관). 이 게이트는 그 실패를 볼 수 없습니다. 진짜 안전망은 06단계의 정합 게이트이고, 그래서 게이트가 실패했을 때의 진단 순서가 여기 intrinsic부터 시작합니다.
출력의 hFOV 손실을 보세요. 10% 초과면 이슈 #16 분기 1 — rectify 대신 Isaac Sim의 opencvPinhole로 왜곡을 모델링할지 검토해야 합니다.

손목캠 hand-eye #14

사람이 입회해야 합니다. 시뮬레이션은 케이블, 클램프, front 카메라 마운트를 모릅니다. 첫 재생은 정지 버튼에 손을 올린 채로 지켜보세요.

테이블에 보드를 고정하고, 손목캠이 여러 자세에서 그것을 봅니다.

# 수동: 팔을 직접 놓고 Enter
python scripts/calibrate_handeye.py --camera wrist --capture

# 자동 재생: sim에서 충돌·가시성 검증된 24포즈. 'move' 입력 확인 후 진행
python scripts/calibrate_handeye.py --camera wrist --capture --replay

python -u scripts/calibrate_handeye.py --camera wrist --solve

결과에서 확인할 것

  • 솔버 간 편차 — 10 mm 초과면 경고가 뜹니다. 솔버가 아니라 포즈 다양성이나 기구학 문제이니 재촬영하세요
  • rig scatter — 고정돼 있어야 할 변환의 흩어짐. 크면 보드가 움직였거나 FK가 실물과 다릅니다

front는 그리퍼 태그로 독립적으로 풉니다(05단계) — 여기 오차가 그쪽으로 전파되지 않습니다.

05

front 카메라 hand-eye — 그리퍼 태그로 #14

사람이 입회해야 합니다. 04와 마찬가지로 로봇이 움직입니다. 시뮬레이션은 케이블·클램프·front 카메라 마운트를 모릅니다.

01에서 그리퍼에 테이프로 고정한 태그를 front 카메라가 여러 자세에서 직접 봅니다. wrist 캘리브레이션과 독립적으로 풀립니다 — 순서를 04보다 먼저 해도 무방합니다. 

# 수동: 팔을 직접 놓고 Enter
python scripts/calibrate_handeye.py --camera front --capture

# 자동 재생: sim에서 그리퍼 태그 가시성 검증된 24포즈
python scripts/calibrate_handeye.py --camera front --capture --replay

python -u scripts/calibrate_handeye.py --camera front --solve

확인할 것

  • 솔버 간 편차 — 10 mm 초과면 경고. 포즈 다양성 부족이나 태그가 촬영 중 흔들렸을 가능성
  • rig scatter — 그리퍼 태그가 실제로 고정돼 있었는지의 물리적 확인. 테이프가 헐거우면 여기서 드러납니다
그리퍼 태그로 잘 안 풀리면(태그가 자꾸 가려지거나 조명이 나쁘거나) 대안이 있습니다: scripts/calibrate_handeye.py --camera front --solve --via-board — 04에서 얻은 손목캠 결과로 테이블 보드를 통해 front 위치를 대신 구합니다. 이 경로는 오차가 wrist 결과 위에 쌓이므로 04를 먼저 잘 끝냈을 때만 씁니다 (문서 위쪽 "태그를 어떻게 고르는가" §5 참고).

정합 게이트 #15

이 작업 전체의 합격 판정입니다.

# 빠른 사전검사 — 렌더러를 거치지 않음
python scripts/verify_alignment.py --camera front --quick \
    --real-image outputs/handeye/front/pose_000.png

# 정식 게이트 — Isaac이 그린 픽셀과 비교
python -u scripts/verify_alignment.py --camera front --gate \
    --real-image <보드가 보이는 프레임>
# → outputs/verify/gate_overlay_front.png
보드를 카메라 쪽으로 기울여 세우세요. 테이블에 눕히면 front 카메라에서 너무 비스듬해 sim 렌더의 마커 셀이 약 4 px로 떨어지고 검출이 실패합니다. 깨끗한 다운샘플링에서는 2.4 px/셀까지 검출되므로 인쇄물 사양 문제가 아니라 렌더 경로의 한계입니다 — 타겟을 다시 만들 필요는 없습니다.

합격 기준

  • 재투영 RMSE < 3 px @ 640×480 — wrist·front 각각
  • 오버레이 이미지로 정성 확인
  • --drift 베이스라인 기록 (이후 세션 체크의 기준선)

불합격 시 진단 순서

  • --quick은 통과하는데 --gate가 실패 → Isaac 쪽. focal_length 환산, convention="ros", T_env_base 확인
  • 둘 다 실패 → 측정 쪽. intrinsic RMS, 솔버 편차, 교차검증 차이를 순서대로
  • --selftest를 다시 돌려 파이프라인 자체가 멀쩡한지 확인 — 참값을 아는 환경에서 실패하면 코드 버그입니다
  • 오버레이에서 일정한 평행 이동은 extrinsic, 배율 차이는 focal length를 가리킵니다
07

조건부 대응 #16

발동 조건이 충족될 때만. 미리 정해뒀으니 현장에서 즉흥 판단할 필요가 없습니다.

발동 조건대응
rectify 후 hFOV 손실 > 10% Isaac Sim 5.1의 OmniLensDistortionOpenCvPinholeAPI로 왜곡을 sim에 주입하는 경로 검토. 단 IsaacLab의 intrinsic_matrices가 거짓을 보고하게 되는 문제를 함께 처리해야 함
스폰 영역이 화면에서 잘림 실물 카메라를 물리적으로 재배치하고 재캘리브레이션. 스폰 범위를 줄이거나 정책에 가림을 떠넘기지 않음
— 현재 front는 스폰 영역 전체를 u 229–383, v 185–307에 담고 있어 발동하지 않습니다

알려진 한계와 남은 결정

  • #8 wrist 렌더 셀프테스트 미해결 열림 — 손목캠이 테이블에 가까워 front와 같은 0.32 m 배치는 보드가 가려지고, 0.14 m로 줄였더니 실패가 아니라 900초 타임아웃으로 멈췄습니다. 원인 미파악. wrist의 수학 자체는 selftest_pipeline.py가 렌더러 없이 커버하므로 현장 작업은 막히지 않습니다.
  • 재학습은 확정적 — 실물 front 프레임을 보니 구도가 sim과 상당히 다릅니다. 정합 후 sim 카메라가 크게 움직이므로, 시각 정책을 만들 때는 새 pose로 데이터를 재생성해야 합니다. (현재 레포에 학습된 시각 정책은 없습니다. main.py·agents/는 전부 state-only입니다.)
  • Orbbec은 화이트밸런스를 V4L2로 노출하지 않습니다 — front의 색 균형은 자동으로 남습니다. 가정 대신 yaml의 exposure.unsupported_controls에 기록됩니다.
  • 실물 큰 큐브가 초록색, sim은 파랑 (0.15, 0.35, 0.85). photometric은 이번 범위에서 실측 기록만 하기로 했으므로 남겨둡니다.
  • temporal(30 Hz 동기·지연)은 별도 세션으로 미뤄둔 상태입니다.
